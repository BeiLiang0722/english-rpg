## 1. 产品目标与成功判定

一句话：**背单词 = 打怪升级**。每个单词是一只怪，答对即命中，连对即连招，答错掉血，清完一局结算金币与 XP，等级和徽章是唯一的进度条。

| 目标 | 可观察判定 |
| --- | --- |
| 正反馈即时 | 从零开始，第 1 次升级必须发生在第 1 局内（≤ 8 题、≤ 5 分钟），必须有全屏升级动效 |
| 零压力 | 不存在任何减少 XP / 金币 / 等级 / 徽章的惩罚；不存在每日配额、签到日历、排行榜、社交比较 |
| 随时中断不丢 | 每题判定后立即落库；任何时刻退出，已得 XP / 金币都保留 |
| 成长可见 | 营地一屏恒常显示 3 个数字：等级+XP 条、已掌握词数、金币（外加连续天数） |

## 3. 路由、全局状态与页面结构映射

### 3.1 设计 token 来源

配色、字体、字号阶梯、圆角、间距、阴影、动效清单、响应式断点、可访问性要求**全部沿用 02 §5–§7 的最终值，本 PRD 不重复**（避免双份数值漂移）。开发时以 02 为唯一 token 出口。

### 3.2 词库 JSON（`public/words.json`）

为与 01 §5.2 的构建脚本产物一致，文件内字段保持 01 的写法；读取进内存后立即映射为小驼峰（映射表见下）。

| JSON 字段 | 内存字段（小驼峰） | 类型 | 非空要求 | 含义 |
| --- | --- | --- | --- | --- |
| `id` | `id` | string | 100% | `w0001` 起，稳定主键 |
| `word` | `word` | string | 100% | 词形 |
| `phonetic` | `phonetic` | string | 100% | 音标 |
| `pos` | `pos` | string | 允许空串 | 词性，用于干扰项同 `pos` 优选 |
| `meaning_cn` | `meaningCn` | string | 100% | 中文释义 |
| `meaning_en` | `meaningEn` | string | 允许空串 | 英文释义 |
| `example` | `example` | string | 100% | 英文例句 |
| `example_cn` | `exampleCn` | string | 允许空串 | 例句中文 |
| `collins` | `collins` | number \| null | 可为 null | 柯林斯星级 |
| `frq` | `frq` | number \| null | 可为 null | 当代语料频率（越小越高频） |
| `tags` | `tags` | string[] | 允许空数组 | `cet4` / `cet6` |
| `audio_url` | `audioUrl` | string \| null | 允许 null | 恒为 null，运行时用设备 TTS |

> **不预存干扰项**：02 §8 曾把 `distractors` 列为待定；定稿为运行时生成（§4.4），词库文件不含该字段。

### 4.4 题型与出题内容引擎（纯函数 `src/game/questionEngine.ts`）

5 种题型的权重、判定与干扰项规则：

| 编号 | 题型 | 出题形式 | 权重 | 判定规则 |
| --- | --- | --- | --- | --- |
| Q1 | 英译中四选一 | 给单词，选中文释义 | 40% | 选项 4 个，正确 + 3 个干扰项；干扰项与正确答案 `meaningCn` **首字不同**，同局内不重复词 |
| Q2 | 中译英四选一 | 给中文释义，选单词 | 25% | 干扰项须与正确答案**首字母不同** |
| Q3 | 拼写填空 | 给中文 + 首字母 + 下划线长度提示 | 20% | 忽略大小写；完全一致 = 正确；编辑距离 = 1 记为**近似正确**（`correct = true`，但 `consecutiveCorrect = 0`、`nextReviewAt` 不推进，不进入错词队列） |
| Q4 | 听音辨词（TTS） | 播放单词读音，四选一 | 10% | 设备无 TTS → 跳过，不扣血、不计题数 |
| Q5 | 例句填空 | 挖空例句中的目标词，给首字母 | 5% | 同 Q3 |

**干扰项生成（运行时，必须写进代码）**：Q1/Q2 从同词库、同 `pos` 的词中随机取 3 个，且与正确答案的首字/首字母不同；同 `pos` 候选不足 3 个时，放宽 `pos` 限制但仍须保证首字（首字母）不同；同一局内已出现的词不入干扰项。

| 函数 | 签名 | 职责 |
| --- | --- | --- |
| `pickQuestionTypes` | `(count, config, ttsAvailable) => QuestionType[]` | 按权重抽题型；Q4 不可用时按比例分摊到其余 4 种 |
| `buildOptions` | `(word, pool, type) => Option[]` | 生成 4 个选项并保证首字/首字母规则与同局不重复 |
| `checkSpelling` | `(input, word) => { correct: boolean; approximate: boolean }` | 忽略大小写 + 编辑距离 1 判定 |

**出题优先级（§5.8 详表）**：每局按优先级排序取前 8 个词；同局内 `wordId` 不重复。

### 4.7 P0-11 连续天数与断签（streak）

| 项 | 内容 |
| --- | --- |
| **触发入口** | ① 进入 `#/boot` / `#/home`（读档完成时）② 每局结算写入时 ③ 商店购买回补卡成功时 ④ 本地日期跨过 00:00 后首次回到营地时 |
| **界面元素** | ① HUD 的「🔥 N 天」② 营地断签保护提示条（仅 `pendingBreak === true`）：「有 1 天可以用回补卡接上，40 金币」+「去商店」按钮，**无红色、无感叹号、无责备词** ③ 冰冻卡生效时的中性 Toast「已自动使用冰冻卡 ×1，连击延续」④ 断连后的固定 Toast（见下表）⑤ 成长页「累计学习天数」与 `longestStreak` 展示 |
| **用户操作** | 无需操作即可获得自动保护（冰冻卡）；点提示条的「去商店」购买回补卡（40 金币）→ 确认弹层 → 连击立即接上；用户**不能**手动指定保护哪一天、也不能关闭保护机制 |
| **系统响应** | 读档与结算两处都调用同一个纯函数 `rolloverStreak(save, now)`（幂等：同一天重复调用结果不变）：算 `gap` → 按判定表决定「不变 / +1 / 消耗冰冻卡 / 归零」→ 更新 `lastStudyDate`、`freezeUsedThisMonth`、`monthlyProtectedDays`、`streakBeforeBreak`、`pendingBreak` → 跨月时重置月度计数器 → 写 `streakChange` 日志 → 落库 |
| **异常情况** | ① 系统日期回拨 → `lastStudyDate` 单调前进，`today < lastStudyDate` 时不触发任何 streak 变更、也不发每日首局奖励（见下表「边界」）② 同一自然日多次读档 → `gap = 0` 分支幂等，不重复消耗冰冻卡 ③ 单月保护额度用尽（`monthlyProtectedDays ≥ 4`）→ 只归零，不再自动消耗冰冻卡，`pendingBreak` 置 `false` ④ 存档缺 `streak` 对象 → 用默认值补齐（`freezeCards = 2`）⑤ 用户改时区导致自然日跳变 → 以设备当前本地日期为准，不做补偿 |

**判定细表**（两处判定必须一致：启动时用于显示、结算时用于真实累加，采用 C16 裁决）。

| 阶段 | 判定逻辑 |
| --- | --- |
| 启动时 | `gap = today − lastStudyDate`（自然日差）。`gap = 0` → `stage = 'done'`（今天已学，streak 不变）；`gap = 1` → `stage = 'pending'`（今天还没打，判定推迟到本局结算）；`gap ≥ 2` → 进入断签处理，结果记入 `stage = 'protected'` 或 `'broken'` |
| 断签处理 | `missed = gap − 1`（真正漏掉的天数）。从最早漏掉的那天起逐日尝试：① 若当月 `freezeUsedThisMonth < 2` → 消耗 1 张冰冻卡，该天视为已学习，`freezeUsedThisMonth++`，`streak` 不减；② 否则视为真断连，`dailyStreak` 归零<br>单月「冰冻 + 回补」合计最多保住 4 天（`monthlyProtectedDays ≥ 4` 时不再消耗冰冻卡） |
| 结算时 | 本局完成后：若 `lastStudyDate === today` → 不变；若 `lastStudyDate === today − 1` → `dailyStreak++`；若 `lastStudyDate < today − 1` → 先按上表完成保护/断连处理，再把 `dailyStreak` 置为 `1`（本局视为新的第 1 天） |
| 断签文案（唯一允许的句子） | 断连后首次进入营地时以 Toast 显示：「连击重新开始了，上次是 N 天。今天继续。」（N = 断连前的 `dailyStreak`，取 `streakBeforeBreak`） |
| 回补卡 | 营地提示条 → 商店购买（40 金币）→ 购买后立即修复**最近 1 天**：`dailyStreak = streakBeforeBreak + 1`、`repairUsedThisMonth++`、`monthlyProtectedDays++`、`lastStudyDate` 前移 1 天。每月限购 2 张，且与冰冻卡合计不超过 4 天 |
| 永不发生 | 连续记录归零的羞辱性弹窗、红色警告、「你已断签 3 天」类提醒文案 |
| 边界 | 用户把系统日期往回改 → `lastStudyDate` 只做单调前进；日期倒退当天不触发任何 streak 变更，也不发放每日首局奖励 |

### 4.8 P0-5 结算页（F3，`#/result/:roundId`）

| 项 | 内容 |

**"首次遇见"与"击败新词"的精确口径**（两者语义不同，可叠加）：
- `seenCount === 0` 在**作答前**判定 → 该题答对给 +5（鼓励认真看新词）。
- `correctCount` 在**作答后**由 0 变 1 → 再给 +5（"击败"了这只怪）。
- 因此"新词首次答对"单题合计 = 基础分 + 5 + 5（例如 Q1 新词首答对 = 10 + 5 + 5 = 20 XP）。

**单局 XP 校验（必须写成单测）**：
- 上限构造：8 题全为 Q3/Q5 且全部答对、8 个词全是新词 → `8×15 + 8×5 + 8×5 + 35（连击 5+10+20）+ 20（每日首局）+ 30（完美局）` = **215**。
- 下限构造：8 题中仅 1 题答对，且该词非新词（`seenCount > 0`）、无任何 bonus → **10**。
- 断言：`10 ≤ roundXp ≤ 215`，并对 215 的构造成例写一条单测。

### 5.4 streak 加成表与连击加成表

**连击加成表（局内 `combo`，01 档位制的唯一定稿口径）**：

| 触发档位 | 触发时刻 | XP | 每局上限 | 代码实现 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 3 连 | `combo` 由 2 变为 3 时 | **+5** | 1 次 | `if (combo === 3 && !comboTiersHit.includes(3)) { xp += 5; comboTiersHit.push(3); }` | 同一段连对中先触发 3 档，继续答对再触发 5 档 |
| 5 连 | `combo` 由 4 变为 5 时 | **+10** | 1 次 | `if (combo === 5 && !comboTiersHit.includes(5)) { xp += 10; comboTiersHit.push(5); }` | — |
| 8 连 | `combo` 由 7 变为 8 时 | **+20** | 1 次 | `if (combo === 8 && !comboTiersHit.includes(8)) { xp += 20; comboTiersHit.push(8); }` | 8 连 = 本局全对，同时满足完美局 +30 |
| 合计 | — | **+35** | — | — | 完美局（8 题全对）连击奖励合计固定 35；单局连击奖励理论上限也是 35（因单局只有 8 题） |

> **歧义澄清**（01 与 02 冲突点，此处定稿）：本 PRD 采用**档位制**（`combo` 达到某档位时给一次固定值），不采用 02 的 `+5×(连对−2)` 连续公式。原因：01 是数值定稿文档，且档位制让单局 XP 上限可精确构造为 215。
>
> **"每档每局仅触发一次"的精确语义（定稿）**：用 `session.comboTiersHit` 记录本局已触发过的档位，**每个档位在整局内最多给奖一次**。因此「连对 4 题 → 答错 → 再连对 4 题」只会拿到 3 档的 +5（第一次触发），第二次连对到 3 时因 `comboTiersHit` 已含 3 而**不再给奖**。这条严格口径同时保证了"单局连击奖励上限恒为 35"，使 §5.1 的 XP 上限 215 在任何作答路径下都成立。

**streak 加成表（`dailyStreak`，对 XP/金币的加成）**：

| `dailyStreak` 区间 | streak 对 XP 的加成 | streak 对金币的加成 | 说明 |
| --- | --- | --- | --- |
| 1–2 天 | **0** | **0** | streak 本身不加成收益，只作展示与徽章条件 |
| 3–6 天 | **0** | **0** | 同上 |
| 7–29 天 | **0** | **0** | 同上 |
| ≥ 30 天 | **0** | **0** | 同上 |

## 7. 边界与异常

### 7.1 同一天重复答题

| 场景 | 行为 |
| --- | --- |
| 同一天连打多局 | 每局独立计算并发放 XP / 金币；`todayFirstRoundDone` 只对**第一局**为 `true`，后续局的 `isFirstRoundToday = false`，因此不再给 +20 XP / +15 金币 |
| 同一天重复出同一词 | 允许（跨局可以重复出词），但**同一局内绝不重复**；已答对且 `nextReviewAt` 未到期的词优先级为 20（巩固），实际很少立刻重现 |
| 同一天对同一词连答 2 次 | `consecutiveCorrect` 会 +2，但 B4/已掌握要求"2 次答对跨 2 个不同自然日"，因此**不会**在同一天被判为已掌握（`prevCorrectAt` 与 `lastCorrectAt` 同日则不满足） |
| 一天内连续购买限购物品 | 受每日限购约束（护心符 2、侦查之眼 1、替身稻草人 1） |
| 跨天瞬间正在答题 | 以**开局时刻**的日期为准：整局按开局那天计入 `dailyStats`、streak、首局判定；`endedAt` 时间戳仍取真实时刻（B8/B9 也按 `endedAt` 判） |

### 7.2 跨天连击结算

| 场景 | 行为 |
| --- | --- |
| `gap = 0`（今天已学再打一局） | `dailyStreak` 不变，不重复计天 |
| `gap = 1`（昨天学过，今天第 1 局） | 结算时 `dailyStreak + 1`，`lastStudyDate = today` |
| `gap ≥ 2` 且冰冻卡充足 | 逐日消耗冰冻卡视为已学，`dailyStreak` 保持并 +1，`freezeUsedThisMonth` 与 `monthlyProtectedDays` 累加，营地显示「已自动使用冰冻卡 ×N」，**无惩罚性文案** |
| `gap ≥ 2` 且冰冻卡不足 | `streakBeforeBreak = dailyStreak`、`pendingBreak = true`（若当月回补额度未满）、`dailyStreak = 0`；下次完成一局后 `dailyStreak = 1`；营地 Toast 文案固定为「连击重新开始了，上次是 N 天。今天继续。」 |
| 单月保护上限 | `monthlyProtectedDays ≥ 4` 时不再消耗冰冻卡，也不再允许回补卡修复 |
| 跨月 | `monthKey` 变化时重置 `freezeCards = 2`、`freezeUsedThisMonth = 0`、`repairUsedThisMonth = 0`、`monthlyProtectedDays = 0`；`pendingBreak` 若跨月则直接结束（不再可回补） |
| 日期回拨 | `lastStudyDate` 单调前进；`today < lastStudyDate` 时不触发任何变更，也不发每日首局奖励 |
| 时区 | 全部按设备本地时区；不做时区转换、不做 UTC 存储（`todayDate` 用本地 `YYYY-MM-DD`） |

### 7.3 localStorage 被清空 / 不可用

| 场景 | 行为 |
| --- | --- |
| 首次打开（无存档） | 建默认档（`level = 1`、`xp = 0`、`coins = 0`、`dailyStreak = 0`、`freezeCards = 2`），直接进营地，**不弹任何引导弹窗** |
| 用户清空浏览器数据 | 等同首次打开，无任何补救提示、无「你的进度丢了」文案 |
| 存档 JSON 解析失败 | 原文备份到 `wordquest.save.v1.bak`，建默认档，Toast「旧存档读取失败，已备份」 |
| 隐私模式 / 写入抛异常 | `persistStatus = 'failed'`，营地常驻提示条「本次进度未保存」，游戏继续可玩 |
| 配额满（QuotaExceeded） | 触发 `rounds` 裁剪：只保留**最近 500 局**（更早的记录聚合进 `stats` 后丢弃），再写一次；仍失败则保持 `failed` 状态 |
| 多标签页同时打开 | 监听 `storage` 事件；检测到其他标签页写入时，当前页 Toast「存档已在其他标签页更新」并在**本局结束后**重新加载存档（不在答题中途打断） |
| 导出/导入 | 导出 JSON 含 `checksum`（对 `payload` 做 SHA-256）；导入时校验失败 → 拒绝并提示「文件校验失败」，**不修改现有存档**；导入成功后合并徽章为并集（保留最早 `unlockedAt`），`stats` 取逐字段最大值防倒退 |

### 7.4 词库答完 / 候选不足

| 场景 | 行为 |
| --- | --- |
| 200 词全部 `seenCount > 0`（无新词） | 优先级 3（新词）自然空置，全部走"巩固"；出题只从 SRS 到期与巩固中取，功能不降级 |
| 200 词全部已掌握 | 仍可继续打；已掌握词按 `nextReviewAt` 升序回到池中作为复习；不做「词库已通关」的终点墙 |
| 高优先级候选不足 8 个 | 按 §5.8 优先级依次下探补齐（错词 → SRS 到期 → 新词 → 巩固） |
| **全池候选不足 8 个**（理论上仅 200 词全在 6 小时冷却内且 SRS 未到期时出现） | **本局题数动态缩减为 N**（N = 实际候选数，最少 1）：进度条显示 `i / N`；`isPerfect` 判定为「全部答对且 N ≥ 6」；`totalQuestions = N` 写入 `RoundRecord`；XP 上下限断言改为 `10 ≤ xp ≤ 215`（N 小则天然不会触顶）；开局前 Toast「本局只有 N 题」 |
| 错词本重练池不足 8 个 | 同上的缩减规则；`source = 'wrongBook'` |
| 词库 JSON 缺失或 200 词校验失败 | 阻止进入营地，`#/boot` 显示「词库文件损坏」+「重新加载」；不允许用空词库开局 |
| Q4 TTS 不可用导致题型不可出 | Q4 从题型池临时移除，权重按比例分配到 Q1/Q2/Q3/Q5；若移除后仍凑不满题数，走缩减规则 |

### 7.5 离线

| 场景 | 行为 |
| --- | --- |
| 完全断网 | 全部核心功能可用（词库是本地 JSON，存档是本地存储）；仅 PWA 首次安装与 Service Worker 更新需要网络 |
| TTS 依赖设备语音包、离线时不可用 | Q4 自动跳过（§7.4），不扣血、不计题数；其他题型不受影响 |
| PWA 缓存 | Service Worker 预缓存 `index.html` / JS / CSS / `words.json` / 音效；版本更新时后台下载，下次打开生效，不打断当前局 |
| 结算后立刻断网 | 所有数据已写本地；无任何上报请求（本 App 无网络上报，埋点全部本地） |

### 8.2 统计页所需的聚合数据

| --- | --- | --- |
| 核心指标卡：总答题数 | `stats.totalQuestions` | 累计写入 |
| 核心指标卡：总正确率 | `stats.totalCorrect / stats.totalQuestions` | 派生（分母 0 显示 `--`） |

**趋势图必须提供文字替代**（02 §7.4）：`<figure>` + `<figcaption>` 文字摘要（如「近 7 天正确率从 62% 上升到 85%」）+「以表格查看」切换输出 `<table>`。

### 11.1 每日任务（`balance.daily`）

**规则**：每天 3 条 = 2 条常驻 + 1 条按本地日期**确定性**轮换。

| 项 | 值 | 说明 |
| --- | --- | --- |
| 条数 | `daily.questCount = 3` | 常驻 2 条（`daily.alwaysIds`）+ 轮换 1 条 |
| 轮换 | 按 `YYYY-MM-DD` 做确定性哈希挑选 | **同一天多次进出营地拿到的清单必须一致**；不得用 `Math.random()`（否则刷新就换题，玩家会以为在做弊） |
| 发奖 | 自动，**无「领取」按钮** | 完成后立刻进账；设计理由是「不做打卡压力、不给忘记领取的惩罚感」 |
| 全清加成 | 3 条全完成 → `+20 金币 / +10 XP`，每日一次 | 幂等键 `daily.questBonusClaimed` |
| 每日上限（派生，非配置项） | 金币 `(5+15) + 15 + 20 = 55/天`；XP `(5+8) + 10 + 10 = 33/天` | 取「2 条常驻 + 当日最肥的 1 条轮换 + 全清加成」；`dev/sim-economy.mjs` 的「设计上限」列按同一口径计算 |

**任务池**（`balance.daily.quests`，`kind` 与 `daily.counters` 的对应关系见下表）：

| id | kind | 名称 | 目标 | XP | 金币 |
| --- | --- | --- | --- | --- | --- |
| `questLogin` | `login` | 今日登场 | 1（打开一次） | 5 | 5 |
| `questAnswer` | `answer` | 练手 8 题 | 8 | 8 | 15 |
| `questCorrect` | `correct` | 答对 6 题 | 6 | 8 | 15 |
| `questPerfect` | `perfect` | 一局全对 | 1 | 10 | 15 |
| `questRound` | `round` | 拿下 2 局 | 2 | 8 | 15 |

| `questCombo` | `combo` | 再连胜 5 次 | 5 | 8 | 15 |
| `questDeck` | `deck` | 碰 6 个新词 | 6 | 8 | 15 |

### 11.7 跨天结算：三个日期键 + 幂等

| 入口 | 调用链 |
| --- | --- |
| 启动 | `main.js` → `actions.loadFromStore()` → `pages.home.enter()` / `game.rolloverDaily()` |
| 每次回到营地 | `home.render()` → `home.enter()` → `game.rolloverDaily()` |
| 开局前 | `flow.createSession()` → `game.rolloverDaily()` + `quest.enterDay()` |

`game.rolloverDaily(save, now)` 做的事（顺序固定）：重置每日标志与限购 → 跨月重置月度计数 → `streak.rolloverStreak()` → `quest.settle()`（任务清单、计数器、宝箱碎片）。

**幂等要求**（三条都必须满足，且都有断言守着）：
1. 同一天重复调用 `settle()` 不重复发奖（`questClaimed` / `questBonusClaimed` / `chestOpenDate` 是幂等键）；
2. 跨天无论跳了几天，只结算一次（依据三个日期键的不等判断）；
3. 同一 `roundId` 重复 `applyRoundEnd` 不重复发奖（`save.rounds` 里已有同 `roundId` 即提前返回）。

**任务进度为什么在结算时重建而不是逐题累加**：`stats.daily[today]` 是今日聚合的**唯一**事实来源，
由它推导 `daily.counters` 天然幂等（重复结算、刷新补结算、中断局都得到同一结果），
不需要 pending 缓冲，也不可能出现「逐题加一次 + 结算再加一次」的双重记账。
代价是任务进度在**一局结束后**更新（营地卡片是打完一局才从 0/8 跳到 8/8），这是有意的取舍。

**每日任务奖励的入账点（易误读，写清楚）**：`quest.grant()` 只记账、**不写 `profile`**，
所以「奖励已经 claimed」不等于「金币已到账」。真实链路是：

| 步 | 发生什么 | 谁负责把金币写进 `profile` |
| --- | --- | --- |
| 1 | 跨天后第一次 `rolloverDaily()` 内部的 `quest.settle()` 会完成「今日登场」并置 `questClaimed` —— 但 `rolloverDaily` **不消费**返回值 | ⚠️ 此步不入账 |
| 2 | 之后 `pages/home.js` 或 `flow.createSession()` 调 `quest.enterDay()` 时该任务已 claimed，幂等返回 `{coins:0, xp:0}` | —— 无需入账 |
| 3 | 当天第一局 `applyRoundEnd()` 里的 `quest.settle()` 汇总出 `questCoins` / `questXp`，写进 RoundRecord 的 `quest` / `questXp` 明细行并连同本局收益一次写入 `profile` | ✅ **入账点** |

因此断言口径是「`profile.coins` 的增量 === 所有明细行之和」（明细行含 `quest`），
`dev/sim-economy.mjs` 的两条「入账链路」断言与「明细外入账恒为 0」就是守这条契约的。

### 11.8 金币 / XP 的入账契约（单一写点）

> 背景：v0.1 存在真实的重复入账 —— `applyRoundEnd` 按「本体 + 全部明细行」算好总额写进 `profile.coins`，
> 而徽章（`achievements.js`）、升级（`level.js`）、任务（`quest.js`）**各自也在直接写** `profile.coins`，
> 三类奖励各发两次；另有一处 `getAllProgress().map(x => x.id)` 取不到 `id`，
> 使「本局新解锁徽章」退化成「全部已解锁徽章」，旧徽章奖励每局重发。详见 `docs/07` §4.1。

**契约**：

| 模块 | 是否直接写 `profile.coins/xp` | 说明 |
| --- | --- | --- |
| `game/balance.js` 的 `applyRoundEnd` | ✅ **唯一写点** | 负责 `earnedCoins = coinsGained + badgeCoins + levelUpCoins + questCoins` 与 `earnedXp` 的最终入账 |
| `game/achievements.js` 的 `checkAchievements` | ⛔（传 `ctx.deferAward:true` 时） | 默认仍就地发奖（商店/开箱路径用）；结算路径传 `deferAward`，只返回 `award:{coins,xp}` |
| `game/level.js` 的 `applyLevelUps` | ⛔（默认） | 只返回 `coinsFromLevels`；需要旧行为可传 `{credit:true}` |
| `game/quest.js` 的 `grant` / `settle` | ⛔ | 只记账，金额由 `settle()` 的返回值 `coinGain`/`xpGain` 带出；非结算入口（营地登录、开局）由调用方**显式入账** |
| `game/chest.js` 的 `open` | ✅ | 开箱是独立事务（不发生在 `applyRoundEnd` 内），自己入账即可 |
| `game/shop.js` 的 `buy` | ✅ | 扣币事务，自己记账 |

**必须成立的不变量**：`roundRecord.breakdown` 里所有 `unit:'coin'` 的行逐行相加，
加上 `roundRecord.coinsGained`，等于本局 `profile.coins` 的实际增量；XP 同理（`xpGained + bonusXp + questXp`）。
这条不变量由 `dev/dom-e2e.mjs` 的两条断言守着，并由 `dev/sim-economy.mjs` 的「明细外的重复入账」列长期监控（应恒为 0）。

### 11.9 单局 XP 上限口径的修正（`[待上游确认]`）

`docs/03` §5.1 写的上限「215」在其自身算式下应为 285（`8×15 + 8×5 + 8×5 + 35 + 20 + 30`）。
v0.2 进一步查明：**285 这个构造本身依赖一个被测出的缺陷** ——
v0.1 的 `applyAnswer` 以每局重置的 `session.progressMap` 为基准，使 `seenCount` 恒为 0，
于是同一词在每一局都被当作新词，「新词首答 +5 / 击败新词 +5」每局重发。

v0.2 已把基准改为 `save.progress[q.wordId]`（同一局内第二次作答该词时用本局已累计值；免费重试回滚到本局快照）。
